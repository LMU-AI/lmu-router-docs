faq:
  - q: IP ホワイトリストとブラックリストを同時に使えますか？
    a: はい。両方を設定した場合、ブラックリストが先に適用されます。IP がホワイトリストに載っていても、ブラックリストに一致すれば拒否されます。
  - q: プライベート（LAN）IP をホワイトリストに入れると接続できないのはなぜですか？
    a: LMU AI のサーバーはプライベート IP（192.168.x.x や 10.x.x.x など）を見ることができず、**あなたの公開出口 IP** しか見えません。`curl https://ifconfig.me` を使って実際の出口 IP を確認し、それを入力してください。
  - q: 自宅の IP が変わります。ホワイトリストはどう使えばよいですか？
    a: 動的な公開 IP をお使いの場合、ISP が割り当てる CIDR 範囲（`123.45.0.0/16` など）を入力して範囲を緩めることができます。範囲を特定できない場合は、ホワイトリストを有効にせず、他の保護（レート制限、総クォータ、モデルホワイトリスト）を利用することをおすすめします。
  - q: LMU AI の API キーが漏洩したらどうすればよいですか？
    a: 直ちにコンソールでキーを**リセットまたは削除**してください。IP ホワイトリストがすでに設定されていれば、漏洩したキーは見知らぬ IP からは使えないため、損失を大幅に軽減できます。また、漏洩元（公開リポジトリのコミット、ログ、チャット履歴、スクリーンショットなど）を追跡し、新しいキーには直ちに IP ホワイトリストを有効にすることをおすすめします。
  - q: 1 つのキーに何個の IP を設定できますか？IPv6 に対応していますか？
    a: "1 行につき 1 ルールです。単一 IP と CIDR 範囲を混在させることができ、エントリ数に厳密な上限はありません。IPv4 と IPv6 の両方に対応しています（IPv6 の例：`2001:db8::/32`）。v4 と v6 の両方の出口がある場合は、両方を入力してください。"
  - q: 本番サーバーからの呼び出しにはホワイトリストをどう設定すればよいですか？
    a: サーバーの**公開 IP**（プライベート IP ではない）を入力してください。ロードバランサーを使っている場合や出口 IP が複数ある場合は、考えられるすべての出口 IP またはその CIDR 範囲をホワイトリストに追加してください。ローカル開発には、干渉を避けるためホワイトリストなしの別のキーを使ってください。
  - q: IP ホワイトリスト、レート制限、総クォータは競合しますか？
    a: 競合しません。むしろ併用することをおすすめします。IP ホワイトリストは「誰が使えるか」を、レート制限は「どれだけ速く」を、総クォータは「どれだけ使えるか」を制限します。本番キーには 3 つすべてを設定して多層防御を実現してください。ホワイトリストが突破されても、レート制限とクォータが最後の砦になります。
  - q: 呼び出しが 403 ACCESS_DENIED で拒否されるのはなぜですか？
    a: IP がホワイトリストに一致しなかった可能性が最も高いです。`curl https://ifconfig.me` で実際の出口 IP を確認し、キーのホワイトリストと照合して、現在の IP を追加するか、一時的にホワイトリストをクリアしてテストしてください。それでも拒否される場合は、ブラックリストに一致していないか、キーが無効化されていないか、クォータが枯渇していないかを確認してください。

キーが漏洩すると、他人がそれを使ってあなたのクォータを消費できてしまいます。**IP ホワイトリスト**は最も直接的な保護であり、信頼する IP だけがキーを使えるようにします。

## 設定する場所

**コンソール → API Keys → 編集（または作成）** に移動し、**IP ホワイトリスト**と**IP ブラックリスト**の 2 つのフィールドを見つけます。

1 行につき 1 ルール、次の 2 つの形式のいずれかで入力します。

| 形式 | 例 | 説明 |
|------|------|------|
| 単一 IP | `203.0.113.10` | 正確に 1 つの IP に一致 |
| CIDR 範囲 | `203.0.113.0/24` | IP の範囲全体に一致（`/24` = 256 個の IP） |

IPv4 と IPv6 の両方に対応しています（IPv6 の例：`2001:db8::/32`）。

## どのように適用されるか

- **ホワイトリストが空** → 送信元の制限なし。任意の IP がキーを使用可能
- **ホワイトリストが空でない** → リスト上の IP のみが使用可能。それ以外はすべて拒否
- **ブラックリスト** → 一致する IP は拒否され、**ホワイトリストより優先**される
- 両方を同時に使用できます（ブラックリストが先にチェックされ、次にホワイトリスト）

拒否されると、API は `403 ACCESS_DENIED` を返します。

## 実際の出口 IP を確認する（重要！）

**これが最も陥りやすい間違いです**：キーに設定する IP は、LMU AI のサーバーが見る**公開出口 IP** でなければならず、コンピューター上の `ipconfig` / `ifconfig` に表示されるプライベートアドレスではありません。

```bash
# Command line
curl https://ifconfig.me
# or
curl https://ip.sb
```

または、ブラウザで [ip.sb](https://ip.sb) / [ifconfig.me](https://ifconfig.me) を開いてください。

<Callout type="warn">
  VPN や会社のプロキシを有効にしたとき、あるいはモバイル端末が Wi-Fi ネットワークを切り替えたときには、出口 IP が変わります。ホワイトリストを設定する前に、上記のコマンドで確認してください。
</Callout>

## よくあるシナリオ

**シナリオ 1：固定のオフィス IP**
```
Whitelist:
203.0.113.10
```

**シナリオ 2：自宅とオフィスの両方から作業する**
```
Whitelist:
203.0.113.10      # Company egress
198.51.100.20     # Home broadband
```

**シナリオ 3：自分のクラウドサーバーで実行する**
```
Whitelist:
<your cloud server's public IP>
```
自分のサーバーだけが API を呼び出せるようにし、ローカル開発には別のキー（ホワイトリストなし）を使ってください。

**シナリオ 4：疑わしい IP を一時的にブロックしたいだけの場合**
```
Blacklist:
1.2.3.4
```
それ以外はいつも通り動作し、通常の使用に影響はありません。

## トラブルシューティング

**Q：呼び出しが 403 ACCESS_DENIED を返します。IP 制限が原因ですか？**

その可能性が最も高いです。順番に確認してください。

1. `curl https://ifconfig.me` で現在の実際の出口 IP を確認する
2. キーのホワイトリストと照合して一致するか確認する
3. 一致しない場合は、現在の IP をホワイトリストに追加するか、一時的にホワイトリストをクリアしてテストする
4. それでも拒否される場合は、ブラックリストに載っていないか、キーが無効化されていないか、クォータが枯渇していないかを確認する

**Q：IP をホワイトリストに入れたのにまだ拒否されます？**

- **プライベート IP**（`192.168.x.x` / `10.x.x.x` / `172.16-31.x.x`）を入力していませんか？公開出口 IP に置き換えてください。
- IPv6 アドレスを入力したのに IPv4 で接続していませんか（またはその逆）？両方を入力してください。
- 形式が不正な CIDR（`1.2.3.4/33` など）を入力していませんか？無効なルールは黙って無視されます。

## 推奨される運用

- **本番キー**には、攻撃対象領域を最小化するために IP ホワイトリストの設定を強くおすすめします
- **開発／デバッグ用キー**ではホワイトリストを省略できますが、必ず**総クォータの上限**を最後の砦として設定してください
- 漏洩が特に心配な場合は、[**レート制限**、**総クォータ**、**モデルホワイトリスト**](/ja/docs/guide/how-to-use-token)と組み合わせて多層防御にしてください
- キーが漏洩した疑いを持った瞬間に、コンソールで直ちに**リセットまたは削除**してください
